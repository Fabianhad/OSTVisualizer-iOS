## 1. CI on GitHub: first full runs (2026-11-20) and what they leave open

`.github/workflows/build.yml` ("Build IPA", job `build-ipa`, image macos-15-arm64, Xcode 16.4 build 16F6, iPhoneOS 18.5 SDK, Apple clang 17.0.0) ran every step to the end for the first time on 2026-11-20 (UTC); two runs passed: run 44654559214 on `5dc7b2b` (57 min 47 s, cold bgfx cache) and run 44661853681 on `787a57d` (4 min 8 s, cache hit; its app executable is byte-identical to the previous run's). Two earlier runs failed in the host tests: 2026-11-16 (Meshing, the FMA failure below) and run 44642251350 on `292c406` (Geometry, a marker-anchor tie whose libm cause is inferred). The steps in job order, with what the runs showed (details in `BUILD.md` and in `PORTING_LOG.md`, entry of 2026-11-20):

1. Xcode selection (`/Applications/Xcode_16.4.app` must exist on the runner image; the step fails with a listing if not) and the Homebrew install of xcodegen and ldid. Both worked on 2026-11-16 and in the runs of 2026-11-20 (Xcode 16.4, build 16F6).
2. **Unit tests on AppleClang** (`cmake -S Config/Tests -B build/tests -DCMAKE_BUILD_TYPE=Debug`, `ctest --no-tests=error`; Debug flags plus `-Os`). This is where the run of 2026-11-16 failed: Meshing 75 of 76, `CurvedMesh.CentreLineMatchesTheWindowsMeshOnTheOracleCases` (zero-length case `zero_len_7`, sample 3), a result that differs between MSVC and AppleClang because of fused multiply-add on arm64. The fix compiles the Core meshing code, the earcut instantiation and some geometry code without FMA contraction (`Core/Geometry/strict_fp.hpp`, `#pragma clang fp contract(off)`, plus `ost_fp::hypot`). It held: Meshing passes on AppleClang 17 arm64 from the first run on the fixed code. That run (44642251350) failed one other test, Geometry `MarkerAnchor.CountTriangleAndCurvedBand`: not contraction but a tie in the marker-anchor search that a last-bit libm difference breaks (cause inferred, not observed on arm64; `PORTING_BLOCKERS.md`, "Not reproducible on iOS"). `5dc7b2b` changed tests and docs only: the assertion accepts the Windows point or its mirror image and a new libm-free test pins the tie rule (1599 tests). All 12 areas pass in the two later runs; the CI run uses the Manifold stub (section 7). If a test differs again, look for contraction in a file that does not include `strict_fp.hpp`, then for a result decided by the last bit of a libm function; never relax a tolerance (the marker-anchor assertion keeps its 1e-9 tolerance and accepts exactly two results, the Windows one and its mirror image, and the case is recorded as not reproducible).
3. libmanifold arm64 check and plist lint. Passed: `libmanifold.a` is thin arm64, iOS, minos 16.0, SDK 18.5; `Config/Info.plist` and `Config/Entitlements.fakesign.plist` pass `plutil -lint`.
4. bgfx, bx and bimg built from the pinned commits (`BGFX_SHA`, `BX_SHA`, `BIMG_SHA`) with `make ios-arm64-release`. The generated makefiles hard-code clang flags that were verified only with Xcode 16.4 (workflow comment). The cold run built bgfx in 25 s and saved the cache (run 44654559214, a cache miss); the next run restored it and skipped the build (the verify steps still ran). The pins are the commits the committed headers were taken from, per the workflow comment; not re-checked.
5. The minos check of the five prebuilt libraries (`libmanifold.a` and the four bgfx libraries) against `EXPECTED_MIN_OS` 16.0: the step fails on any object with a higher minos. Passed in both full runs: every object is arm64, iOS, minos 16.0 (`libmanifold.a` 15 objects; bgfx 22, bx 22, bimg 24, bimg_decode 1).
6. `xcodegen generate` from `project.yml`, then the readback of `-Os` (`GCC_OPTIMIZATION_LEVEL` s) and the 16.0 deployment target from the generated project for both configurations. Passed: one target; `GCC_OPTIMIZATION_LEVEL = s` and `IPHONEOS_DEPLOYMENT_TARGET = 16.0` read back for Debug and Release.
7. `xcodebuild` (iphoneos, Release, signing off). BUILD SUCCEEDED in both full runs: 88 translation units (4 clang response files, every one with `-Os` and no other `-O` level), one link with clang++. This was the first compile of the Objective-C/Objective-C++ sources against the real SDK: no error (warnings: section 2). No "built for newer iOS version" linker warning appeared; the only linker warning is `ld: warning: ignoring duplicate libraries: '-lc++'`.
8. Bundle checks: executable `OST Visualizer`, bundle id `com.fabian.ostvisualizer`, `MinimumOSVersion` 16.0, arm64 only, no `*.sc` in the bundle. Passed in both full runs.
9. `ldid` fake-sign with `Config/Entitlements.fakesign.plist` (only `get-task-allowed`); the step fails if any entitlement key matches `memory|jetsam|extended-virtual-addressing`. Passed: the signed entitlements hold `get-task-allowed` = true only.
10. IPA packaging and artifact upload (`OST-Visualizer-ipa`, 30 days). Passed: 1,963,627 bytes, one app `Payload/OST Visualizer.app`; the downloaded artifacts of both runs were inspected locally with a parser (nothing executed): zip integrity, Info.plist, thin arm64 Mach-O with minos 16.0, and the ad hoc code signature, whose SHA-1 and SHA-256 page hashes match the file.

Still open after the runs (what CI cannot check): install and launch of the IPA, and whether the owner's installer accepts the fake signature (only the structure and hashes were checked; iRAM+ memory entitlements are applied by the owner afterwards); everything at runtime (crashes, Metal/bgfx rendering and shaders on a GPU, picking, frame time and memory, large projects); the 25 fixed-ui-unverified device checks and `.ost`/`.osp` open-in with the document picker; real Manifold on AppleClang through the host tests (the CI host tests use the stub) and Manifold on a device; the Debug configuration (its settings were read back, only Release was compiled) and an iOS Simulator slice (not built); real `.ost`/`.osp` project files (the repo holds only synthetic oracles and two CAB files). The libm cause of the marker-anchor tie is inferred, not observed on arm64: on a device the negative marker of an exactly mirror-symmetric curved band may sit one grid cell (4.85 points at the test scale) on the other side of its axis than on Windows.

The syntax check used hand-written stubs for Foundation, CoreFoundation, CoreGraphics, QuartzCore, UIKit and UniformTypeIdentifiers, and a macOS target (so `TARGET_OS_IPHONE` is 0; the sources contain no such conditionals). ## 7. Test infrastructure and follow-ups

- Run the host tests on the macOS CI runner with each push (in `build.yml`; done since 2026-11-20: 12 of 12 areas pass on AppleClang 17 arm64, the step takes 168 s since the build is bounded to the runner's core count, 64 s of it ctest); add a run with `-DOST_TEST_BOOLEAN=ON` there if real Manifold should be covered on AppleClang (the default CI run uses the boolean stub; 9 Export and Meshing tests only run with it, and 1 Meshing test only runs without it, so the total goes from 1599 to 1607; 1598 to 1606 on 2026-11-19). There is no iOS Simulator test target and no automated UI test.
- Real `.ost` and `.osp` fixtures (none in the repo) would turn the oracle-table tests into end-to-end import tests.
- CI notes from the runs of 2026-11-20: `build.yml` runs on every push to any branch and on `workflow_dispatch`, with `permissions: contents: read` and a 90-minute timeout; its `concurrency` group is per ref with `cancel-in-progress: true`, so a newer push to the same ref cancels a run in progress. Every run carries a warning that Node.js 20 is deprecated: `actions/checkout@v4`, `actions/cache@v4` and `actions/upload-artifact@v4` are forced to run on Node.js 24 (a warning, not a failure; a later bump of the action versions may be needed). The runner size (3 cores, about 7 GB) is what GitHub documents for this standard runner size, not measured: the job log does not print it. The host-test build is bounded with `--parallel "$(sysctl -n hw.ncpu)"` (`787a57d`): a bare `--parallel` is an unlimited `make -j` and took 55 min 20 s instead of 168 s, so keep it bounded.
- Cleanup noted by the wiring wave, no behaviour change: four near-identical "present an OK alert from the top-most presented controller" helpers in `ViewController` categories; `PlanView.mm` `isCountLike()` repeats a test in `Core/Geometry/takeoff_footprint.cpp`; functions with no caller kept by tests (`ost_store::shift_condition_ref_nos`, `ImportService +loadProjectWithUID:`, `ost_meshing::generate_takeoff_meshes`, `RenderConfig::is_ost()`); a project is loaded twice on open (preflight in `DatabaseViewController`, then `ViewController`); the edit pan hit-tests at the recognition location, not at touch-down.
- Rule for any further parity work: test first. Port the Windows test into `Config/Tests/<Area>/test_*.cpp` with the same inputs and expected values (conventions in `Config/Tests/README.md`), watch it fail on the iOS code, then fix. Never relax a tolerance to make a port pass; a failing port is an iOS bug or a Windows ambiguity to report. If a Windows behaviour looks accidental, inconsistent or unsafe, do not port it: keep the iOS behaviour and list it with the Windows file:line.
