### The 8 former formal items (all kept, no code change; status wont-fix)

#### 1. DBP-04 / DBP-05 (aliases SNP-01, LP-19, LOAD-01): a stored `TakeoffIncrements` of exactly 0

- **Decision**: a stored `Bids.TakeoffIncrements` of exactly 0 (also 0.0 and -0.0) keeps meaning snapping off on iOS; a NULL value loads as 1.0 like Windows (LOAD-01 is also an alias of DBP-03, which stays as it is).
- **Windows**: `ost_visualizer/infrastructure/mdb/components/hierarchy_reader.py:126` (`float(bid_row.TakeoffIncrements or 1.0)`, the loader the plan view uses) turns 0 into 1.0; `ost_visualizer/presentation/components/plan_view/view.py:3955-3962` (`set_snap_settings`) treats `<= 0` as snapping off; `ost_visualizer/infrastructure/mdb/components/settings_reader.py:151` and `ost_visualizer/presentation/dialogs/cover_sheet/dialog.py:2385-2388` keep 0. No Windows test pins a stored 0 through the loader.
- **iOS**: `Core/Persistence/ProjectStore/Components/ProjectStore+Load.cpp:378` keeps a stored value (0 stays 0 = snapping off, `Bid::snap_increments_ost`, `Core/Domain/Bid.hpp:24`: a value <= 0 means off), `:380` loads NULL as 1.0.
- **Pinned by**: `Dbp05_TakeoffIncrementsZero.ZeroKeepsSnappingDisabledUntilTheOwnerDecides` (`Config/Tests/Persistence/test_load_fields.cpp:63`) (the test name predates the decision), `Dbp04_TakeoffIncrements.NullLoadsAsOneInch` (`Config/Tests/Persistence/test_load_fields.cpp:48`), `Dbp04_TakeoffIncrements.SnapIncrementFollowsTheMeasurementSystem` (`Config/Tests/Persistence/test_load_fields.cpp:80`).
- **To follow Windows instead (not planned)**: one condition in `ProjectStore+Load.cpp:378-380`: also load 1.0 when the stored value is 0; flip the test.
- **possible Windows defect**: `ost_visualizer/infrastructure/mdb/components/hierarchy_reader.py:126`: two Windows readers disagree on a stored 0 (the plan-view loader gives 1.0, the Cover Sheet reader and dialog keep 0) although the plan view supports `<= 0` as snapping off; through the database "off" is unreachable. Table below.

#### 2. BRW-09 (alias DBP-22): restore from Deleted Bids when `OrigBidProjectUID` names a folder that no longer exists

- **Decision**: the bid is restored unassigned (Windows refuses the whole restore group).
- **Windows**: `ost_visualizer/presentation/handlers/project_write_handler.py:580-610` (`restore_bids` groups the bids by original project; the failure dialog "Restore Error", "Failed to restore bids." is at :604-609) and `ost_visualizer/infrastructure/mdb/components/project_operations.py:38-45` (`move_bids_to_project` refuses a missing target or original project before any change, so the WHOLE restore group fails and the bid stays in the trash). Windows tests pin the refusal: `tests/infrastructure/mdb/components/test_project_operations.py:124` and `:140`.
- **iOS**: `ost_store::restore_bid` (`Core/Persistence/ProjectStore/ProjectStore.cpp:322`) restores such a bid unassigned, which is what the iOS Restore action always did (menu entry `Controllers/DatabaseViewController.mm:571`).
- **Pinned by**: `Brw09_Restore.AfterTheOriginalFolderWasDeletedTheBidComesBackUnassigned` (`Config/Tests/Browser/test_trash_restore.cpp:180`), `Brw09_Restore.InterimADanglingOriginalFolderRestoresTheBidUnassigned` (`Config/Tests/Browser/test_trash_restore.cpp:217`).
- **To follow Windows instead (not planned)**: in `restore_bid`, roll back and return false when `OrigBidProjectUID` is set but the folder row is missing (today the JOIN simply finds no target); `DatabaseViewController.mm:583` already shows the failure alert when the call returns NO. Flip the tests.
- **Possible Windows defect**: none. Judged a deliberate referential-integrity rule: a dangling reference cannot arise inside Windows because deleting a project clears it (`ost_visualizer/infrastructure/mdb/components/project_operations.py:190-199`). Weakness only for foreign data: such a bid can never be restored on Windows and the dialog blames a locked database.

#### 3. EXP-12: control characters in names of exported OBJ groups, materials and DXF layers

- **Decision**: control characters (U+0000-U+001F, U+007F) are dropped from those names; Windows keeps them.

- **Pinned by**: `ExportText.SanitizeMaterialNameDropsControlCharactersUnlikeWindows` (`Config/Tests/Export/test_export_text.cpp:29`), `ObjWriter.GroupAndMaterialNamesAreSanitisedLikeWindows` (`Config/Tests/Export/test_obj_writer.cpp:150`).

#### 4. EXP-13 (alias MSH-M02): OBJ face winding when the export holds a negative

- **Decision**: every exported OBJ mesh stays outward-facing, with or without a negative of another type in the export. Same line as the decided EXP-M02, GEO-15 and EXP-17.
- **Windows**: `ost_visualizer/presentation/visualization/core/boolean_operations.py:10-12` (`_flip_manifold_faces`) and `:49-61` (without a negative the input is returned as built; otherwise EVERY returned mesh is flipped), `cpp_extensions/src/module_geometry.cpp:95-103` (a positive without a same-type negative comes back untouched, with the generator's winding), `ost_visualizer/presentation/visualization/exporters/adapters/obj_writer.py:38-43` (`_transform_faces` swaps every face). Re-executed for the research: without a negative the wall is +48000 and the slab +40000 (outward); with a negative of another type the untouched wall is -48000 (inward) next to the cut slab +36400 (outward): one Windows OBJ mixes both windings. The only Windows test of the flip mocks `boolean_union` (`tests/presentation/visualization/core/test_boolean_operations.py:11`).
- **iOS**: every mesh stays outward-facing (`Core/Meshing/BooleanPass.hpp:60`, `Core/Meshing/gen_count.cpp:97`, `Core/Meshing/gen_curved.cpp:14`).
- **Pinned by**: `ObjWinding.BooleanResultsStayOutwardFacingWithANegativeInTheExport` (`Config/Tests/Export/test_obj_writer.cpp:360`), `ObjWinding.ExportedMeshesHaveThePositiveSignedVolumeOfTheWindowsObj` (`Config/Tests/Export/test_obj_writer.cpp:264`), `ObjWinding.EveryCurvedWallAndCylinderVariantIsOutwardFacing` (`Config/Tests/Export/test_obj_writer.cpp:329`).
- **To follow Windows instead (not planned)**: not a one-line change. `Core/Meshing/BooleanPass.cpp` (or `ExportMeshSet.cpp`) would have to reverse the faces of every surviving positive when the scene holds a negative and the OBJ writer would have to write faces as `(f0, f2, f1)`; it would also contradict the GEO-15 and EXP-17 decisions. Only needed if byte-identical OBJ winding with negatives is wanted.
- **possible Windows defect**: `ost_visualizer/presentation/visualization/core/boolean_operations.py:10-12`: the flip is applied to meshes with two different windings, so adding a negative of another type turns every untouched positive inside-out. Table below.

#### 5. EXP-16: the raw condition name in the OBJ and MTL comment lines

- **Decision**: CR and LF of a condition name are written as a space in the `# <name>` comment lines of the OBJ and the MTL; Windows writes the name raw.
- **Windows**: `ost_visualizer/presentation/visualization/exporters/obj_exporter.py:46` (MTL `# {original_name}`) and `:70` (OBJ), with `original_name` the raw condition name (`base_exporter.py:135-146`). A name with CR or LF ends the comment and the rest becomes OBJ or MTL statements. The Windows tests use only a plain name (`tests/presentation/visualization/exporters/test_obj_exporter.py:23-83`).
- **iOS**: `OBJWriter::single_line` (`Core/Export/obj_writer.cpp:130`) writes CR and LF as a space and every other character as it is; used for the OBJ comment line (:167) and the MTL comment line (:205). The rest of the OBJ and MTL text equals Windows byte for byte.
- **Pinned by**: no host test passes a name with CR or LF through `OBJWriter`: this kept rule is not pinned by a test (test gap).
- **To follow Windows instead (not planned)**: make `single_line` return its argument unchanged. Recommended: keep.
- **possible Windows defect**: `ost_visualizer/presentation/visualization/exporters/obj_exporter.py:46`: the comment lines are written from the raw name; a name with a line break defines extra materials or selects them (also :70). Table below.

#### 6. IMP-20: three sub-behaviours of the DATETIME and binary column rule

- **Decision (all three kept)**: (1) a DATETIME integer outside the C int range (for example `99999999999 1 1 0 0 0`) stores NULL and the import goes on; (2) `BidTexts.Name` and `BidCallOuts.Name` are stored as UTF-8 text; (3) memo and IMAGE (long binary) text columns stay TEXT. The decided date rule itself (a six-part string is kept as text, NULL when it is not a valid date) is done and tested. IMP-05 (an integer of more than 64 bits fails the import, like Windows) is unchanged and was not part of this decision.
- **Windows**, all in `ost_visualizer/infrastructure/mdb/components/`: `import_operations.py:594-610` (catches only `(ValueError, TypeError)` at :608: an `OverflowError` escapes and the whole import fails and rolls back; the Windows test `tests/infrastructure/mdb/components/test_import_operations.py:3079-3084` calls it a characterisation with an open owner question); names as latin-1 bytes: `import_operations.py:614-615` with `serialization.py:5-8` and `:70-81` (`encode_annotation_text`, raises for any character outside latin-1, for example the euro sign); memo and IMAGE text as a UTF-8 BLOB: `import_operations.py:611-616` with `serialization.py:54-67`.
- **iOS**: `Core/Persistence/ProjectStore/Components/ProjectStore+ImportWriter.cpp:153` (`is_valid_datetime`), `:188-196` (date column rule: raw six-part text, else NULL) and `:198-207` (names stay text, memo and IMAGE text kept as TEXT); `Core/Persistence/OstSchema.cpp:1302` (datetime conversion) and `:519` (BidTexts table); `Core/Persistence/OstSchema.hpp:45` (column type contract). - **Pinned by**: (1) `ImportColumnTypes.Imp20_AnIntegerBeyondTheCIntRangeReadsAsNullInsteadOfFailingTheImport` (`Config/Tests/Import/test_import_column_types.cpp:120`), `ImportColumnTypes.Imp20_AnOverflowingDateReadsAsNullAndTheImportGoesOn` (`Config/Tests/Import/test_import_column_types.cpp:343`), `ImportColumnTypes.Imp20_AnythingElseReadsAsNull` (`Config/Tests/Import/test_import_column_types.cpp:98`), `ImportColumnTypes.Imp20_AValidSixPartDateKeepsItsRawText` (`Config/Tests/Import/test_import_column_types.cpp:86`), `ImportColumnTypes.Imp20_TheConversionMatchesTheWindowsFunctionOnEveryOracleValue` (`Config/Tests/Import/test_import_column_types.cpp:144`); (2) and (3) `ImportColumnTypes.Imp20_TheColumnTablesAreTheWindowsSchemaColumns` (`Config/Tests/Import/test_import_column_types.cpp:220`), `ImportColumnTypes.Imp20_MemoTextAndDatesOfTheBidTablesAreConverted` (`Config/Tests/Import/test_import_column_types.cpp:322`), `ImportColumnTypes.Imp20_EmptyMemoAndBinaryValuesAreNullAndTextIsKept` (`Config/Tests/Import/test_import_column_types.cpp:195`), `ImportColumnTypes.Imp20_TheTableInfoReportsTheWindowsTypeOfEveryDatetimeAndImageColumn` (`Config/Tests/Import/test_import_column_types.cpp:265`). - **To follow Windows instead (not planned)**: only needed if an OST or Windows-format export is added or the Windows byte format must be kept. (1) is a change in `is_valid_datetime`; (2) and (3) change the memo / long binary branch of `import_convert_value` (`ProjectStore+ImportWriter.cpp:198-207`) and add blob binding to `OstDatabase`.
- **possible Windows defect**: (1) `ost_visualizer/infrastructure/mdb/components/import_operations.py:594-610`: a date that is out of range reads as NULL but an integer beyond the C long range raises an uncaught `OverflowError` and aborts the whole import; (2) the same latin-1 rule inside the Windows app, `ost_visualizer/infrastructure/mdb/components/annotation_operations.py:255-257`: text and callout annotations with characters outside latin-1 cannot be saved. #### 8. RPV-29: the view-dependent normal flip in the 3D lighting

- **Decision**: option (a), keep the flip; the shaders are not changed.
- **Windows**: `ost_visualizer/presentation/visualization/utils/mesh.py:70-80` (`_normalize_vector`: `if nz < 0.0` negate, at :78-79, so horizontal faces are always lit as facing up; used through `prepare_vertices_for_shading`) and `cpp_extensions/src/renderer/renderer.cpp:616-626` and `:652-658` (fragment shaders: raw normal, `max(dot, 0)`, no flip, no culling).
- **iOS**: `Rendering/Shaders/src/fs_mesh.sc:13` and `Rendering/Shaders/src/fs_oit_accum.sc:13` flip the normal towards the viewer (`if (dot(N, V) < 0.0) N = -N;`). The lighting constants and directions are the Windows ones (`Rendering/Renderer.mm:580`: ambient 0.55, key 0.45, fill 0.35, rim 0.2).
- **Why the flip stays**: deleting it does not reproduce Windows. The Windows normal is +z-oriented and winding-dependent on vertical faces, while Windows meshes are inward-facing and iOS meshes outward-facing by the GEO-15, EXP-M02 and MSH-21 decisions (for the far bottom face of a transparent box: 1.012 with the flip, 0.691 without, per the fixer's calculation).
- **Pinned by**: nothing: not host-testable (no `shaderc`, no Metal device here); the look was never compared on a device.
- **To follow Windows instead (not planned)**: (b) literal Windows shader: delete the flip in both shaders; (c) replace it by `if (N.y < 0.0) N = -N` (the Y-up form of `nz < 0`). Both need the two generated shader headers (`Rendering/Shaders/generated/fs_mesh.h`, `fs_oit_accum.h`) regenerated with the `shaderc` of the pinned bgfx commit (`BUILD.md`) and a look on a device.
- **Possible Windows defect**: none of its own. Judged deliberate and test-pinned (`mesh.py:70-80`; `tests/presentation/visualization/utils/test_mesh.py:162-168`); the winding-dependent lighting on Windows follows from the winding inconsistency recorded under EXP-13, EXP-17 and EXP-M02 in the table below.

The only calls in that path whose result can differ between platforms are `atan2`, `cos` and `sin` (Windows CRT against Apple libm); no fused multiply-add is emitted for the two files involved (checked on an aarch64-macos build with zig clang 22), and nudging one of the 53 libm results of the test case by one ulp flips the answer in 23 of 106 cases, to the value CI reported (20 of the 23 bit for bit, the rest within 2 ulp). Making the result equal to the MSVC CRT's was not attempted: it would mean in-tree `atan2`, `sin` and `cos`, which changes numerics everywhere (the owner's decision). No rule differs: an exact tie keeps the first candidate on both sides (Python `min` and the strict `<` of the C++), which `MarkerAnchor.AnExactTieKeepsTheFirstCandidateOfTheWindowsOrder` pins with dyadic inputs and no libm call. `MarkerAnchor.CountTriangleAndCurvedBand` accepts the Windows point and its mirror image. No app code changed. On a device the marker of an exactly symmetric curved band can therefore sit one grid cell to the other side of its axis than on Windows; the owner may want to look at it.

## Open for the owner after the two device bugs (found 2026-11-20, nothing of this was changed)

- **The transparent look.** The Windows renderer draws an opacity of 0.5 almost opaque: its accum and revealage shaders weight the alpha twice (renderer.cpp 647, 666, 2270, 718-719), the mesh share is about 0.997 at the fit distance (0.995 for a scene of size 3). The iOS shaders give a coverage of 1 - prod(1 - alpha), 0.5 for one layer: half see-through. Matching Windows means new fs_oit_revealage / fs_oit_composite shaders (shaderc is not available here; the headers come from `build-bgfx-ios.yml`). Computed from the Windows source, Windows not run.
- **When the camera is refit (CAM-02, CAM-03, closed decisions).** The far plane now reaches a scene that appears without a refit, but the camera still looks where it looked: if the first selected 3D page has no takeoffs the scene appears out of view until Reset. Windows frames the first non-empty scene of a bid (`mesh_view.py _initialize_camera_for_current_scene`).
- **The portrait crop of the fit.** The fit distance is 1.80278 times the size (Windows show_object, no aspect); on a phone in portrait about 39 to 47 percent of the vertices lie inside the side planes (pages of ratio 48 and more), at 4:3 all of them.
- **A condition picked in the Conditions list highlights its takeoffs as a group** (iOS only; Windows selects nothing, the sidebar only starts a place session; the "Select Objects" commands are explicit). A drag of one of them moves the group. Delete does nothing in that state, where Windows would delete the explicitly selected takeoffs.
- **Undo and redo clear without the Windows page check.** The undo of a Delete selects only while its page is on screen (like Windows `_history_selection_owner`); the redo of a Delete and the undo of a Place clear the selection whatever page is shown (Windows: only while the page that owned the step is current). The safe direction.
- **The clear after Delete drops the condition highlight also in Place mode** (the placement tool keeps its condition). iOS has one highlight field and cannot tell who owns it; Windows keeps a highlight that a placement session owns.
- **UND-10 selects one takeoff**, Windows selects every restored takeoff (the parent and its holes).
- **The depth range of an unfitted scene.** The far plane can be thousands of units while the near plane scales with the camera distance (0.06 at the start): coplanar faces may flicker until the first fit. `Mat4::perspective` builds an OpenGL style depth range although Metal clips z to 0..1 (unchanged by this job): everything nearer than about twice the near plane is clipped.
- **No on-screen diagnostic was added.** The cause of bug 1 is a definite defect found by reading the code and confirmed by every reviewer, but it is GPU behaviour that cannot be run here; if the transparent meshes are still invisible after this build, the diagnostic line (mesh count per stage, bounds, camera distance, near/far, OIT availability) is the next step. Two `NSLog` lines were added instead (an unusable OIT framebuffer, a failed scene generation).
