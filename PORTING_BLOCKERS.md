COND-ELEV-01, the closing-inch-mark rule (`ost_visualizer/presentation/dialogs/edit_condition_dialog.py:72`, the block `:1437-1461`, the refusal `:1444-1445`):

- (1) One ASCII `"` anywhere in the text switches the whole rule off (`'"' not in elev_value`, `:1444`), so the silent truncation the rule exists to prevent still happens with a stray quote: `5'x"`, `5'6x"`, `5'abc"` and `5'x1/2"` save as 60 inches, `10'6.3"` saves as 120 and `6"5'7` saves as 60.
- (2) The character class is ASCII only (`[0-9A-Za-z]`, no `IGNORECASE`): `5'` followed by e acute, `_`, Arabic-Indic three (U+0663), fullwidth six (U+FF16), U+017F, U+212A or a CJK character is accepted as 60 inches although something non-blank follows the mark.
- (3) U+201D and U+2033 (and U+201C, U+2019) do not count as an inch mark: `5'6` with U+2033 is refused, `5'6` with U+2033 and `"` is accepted.
- (4) The lone-x exemption needs the x to be the last non-blank character of the whole text and is decided per foot mark: `5'x` is accepted, `5'x'` refused, `5'_'x` accepted; U+200B, U+FEFF and U+180E after the x are not white space for Python's `\s`, so `5'x` followed by one of them is refused.
- (5) The `\s*` between the mark and the character is unreachable for a first foot mark (the shared parser refuses that text first) and `$` is redundant after `\s*` (harmless).
- (6) Pre-existing, not new: the dialog catches only `ValueError` (`:1442`), so a feet run beyond the float range raises an uncaught `OverflowError` in the Windows slot (checked in memory: it raises); iOS refuses it with the normal message (an existing deliberate deviation, `CondElev01_Validation.AFeetRunBeyondTheFloatRangeIsRefusedWithTheNormalMessage`).
- (7) Consequence for stored data (parity, owner-visible, note l): a stored name such as `Footing @T 5'6` opens with `5'6` in the Elevation field and EVERY dirty save of that condition is refused until the elevation is fixed or cleared. Windows validates the whole form on every dirty save (`_apply_changes` `:1760-1765`: `if not self._dirty: return True`, then `_validate_and_build_dto`, whose refusal returns None; `_on_ok` `:1823-1827` then does not close); iOS does the same (`EditConditionViewController.mm` `_applyChanges`, `if (!_dirty) return YES; if (![self _validateAndCollectTextFields]) return NO`, `:359-363`). ### Not reproducible on iOS
- **EXP-24** (cannot-reproduce): the DXF LINE entity order is the iteration order of a `std::unordered_set` (`Core/Geometry/feature_edges.cpp:124`, `Services/ExportService.mm:151`); it differs between STL implementations (Windows MSVC and libc++) and cannot be matched. The DXF content is the same, only the order of the lines differs.
- **Qt-specific results** (decided items above): the Qt path clipper tolerance band and point order (GEO-M02, RPV-27 (a)) and the scene-pixel evaluation (GEO-M02) have no iOS counterpart.
- **Marker anchor tie on a mirror-symmetric curved band** (RPV-27, the negative marker anchor; not reproducible bit for bit across platforms; found by the first GitHub run of the 7-commit push, 2026-11-20, run 44642251350): when the centroid of a curved linear takeoff lies outside the band, Windows `_nearest_interior_anchor` takes `min(candidates, key=squared distance)`, the first of the nearest grid centres. On a band that is mirror symmetric the two best centres are mirror images; in the doubles their squared distances come out bit-identical on the x86-64 builds here, so the first (left) one wins, as on Windows, and a last-bit change in the arc points breaks the tie. The AppleClang arm64 run gave the mirror one, 4.85 points (one grid cell) on the other side of the axis (72.5756 against 77.4244). Cause: inferred, not observed on arm64. The only calls in that path whose result can differ between platforms are `atan2`, `cos` and `sin` (Windows CRT against Apple libm); no fused multiply-add is emitted for the two files involved (checked on an aarch64-macos build with zig clang 22), and nudging one of the 53 libm results of the test case by one ulp flips the answer in 23 of 106 cases, to the value CI reported (20 of the 23 bit for bit, the rest within 2 ulp). Making the result equal to the MSVC CRT's was not attempted: it would mean in-tree `atan2`, `sin` and `cos`, which changes numerics everywhere (the owner's decision). No rule differs: an exact tie keeps the first candidate on both sides (Python `min` and the strict `<` of the C++), which `MarkerAnchor.AnExactTieKeepsTheFirstCandidateOfTheWindowsOrder` pins with dyadic inputs and no libm call. `MarkerAnchor.CountTriangleAndCurvedBand` accepts the Windows point and its mirror image. No app code changed. On a device the marker of an exactly symmetric curved band can therefore sit one grid cell to the other side of its axis than on Windows; the owner may want to look at it.

## Open for the owner after the two device bugs (found 2026-11-20, nothing of this was changed)

Verified by GitHub run 44678523124 (success): the code of the two fixes (`34e14c9`, Delete clears the selection; `aef35d8`, transparent meshes are drawn) builds against the real iPhoneOS SDK and its host tests pass (B-010); runs 44856186199 and 44953904172 (success) built and tested the code on top of it. What the fixes do on a device is not verified, and the points below are unchanged.

- **The transparent look.** The Windows renderer draws an opacity of 0.5 almost opaque: its accum and revealage shaders weight the alpha twice (renderer.cpp 647, 666, 2270, 718-719), the mesh share is about 0.997 at the fit distance (0.995 for a scene of size 3). The iOS shaders give a coverage of 1 - prod(1 - alpha), 0.5 for one layer: half see-through. Matching Windows means new fs_oit_revealage / fs_oit_composite shaders (shaderc is not available here; the headers come from `build-bgfx-ios.yml`). Computed from the Windows source, Windows not run.
- **When the camera is refit (CAM-02, CAM-03, closed decisions).** The far plane now reaches a scene that appears without a refit, but the camera still looks where it looked: if the first selected 3D page has no takeoffs the scene appears out of view until Reset. Windows frames the first non-empty scene of a bid (`mesh_view.py _initialize_camera_for_current_scene`).
- **The portrait crop of the fit.** The fit distance is 1.80278 times the size (Windows show_object, no aspect); on a phone in portrait about 39 to 47 percent of the vertices lie inside the side planes (pages of ratio 48 and more), at 4:3 all of them.
- **A condition picked in the Conditions list highlights its takeoffs as a group** (iOS only; Windows selects nothing, the sidebar only starts a place session; the "Select Objects" commands are explicit). A drag of one of them moves the group. Delete does nothing in that state, where Windows would delete the explicitly selected takeoffs.
- **Undo and redo clear without the Windows page check.** The undo of a Delete selects only while its page is on screen (like Windows `_history_selection_owner`); the redo of a Delete and the undo of a Place clear the selection whatever page is shown (Windows: only while the page that owned the step is current). The safe direction.
- **The clear after Delete drops the condition highlight also in Place mode** (the placement tool keeps its condition). iOS has one highlight field and cannot tell who owns it; Windows keeps a highlight that a placement session owns.
- **UND-10 selects one takeoff**, Windows selects every restored takeoff (the parent and its holes).
- **The depth range of an unfitted scene.** The far plane can be thousands of units while the near plane scales with the camera distance (0.06 at the start): coplanar faces may flicker until the first fit. `Mat4::perspective` builds an OpenGL style depth range although Metal clips z to 0..1 (unchanged by this job): everything nearer than about twice the near plane is clipped.
- **No on-screen diagnostic was added.** The cause of bug 1 is a definite defect found by reading the code and confirmed by every reviewer, but it is GPU behaviour that cannot be run here; if the transparent meshes are still invisible after this build, the diagnostic line (mesh count per stage, bounds, camera distance, near/far, OIT availability) is the next step. Two `NSLog` lines were added instead (an unusable OIT framebuffer, a failed scene generation).
